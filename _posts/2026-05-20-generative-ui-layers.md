## 前回の続き：OpenUIだけでは、まだ“その場アプリ”にならない

前回、[OpenUIを触ってわかった：アプリ屋の仕事は“画面作り”から“生成の柵作り”へ移る](/ebisuke-blog/2026/05/17/openui-generative-ui-smoke/) という記事を書いた。

OpenUIで面白かったのは、LLMが自由なHTMLを吐くのではなく、OpenUI Langという中間表現を返し、それをRendererがUIとして描画するところだった。生成されたものが人間に読める。レビューできる。保存できる。差分も取れる。

でも、あの記事の最後にも書いた通り、まだ足りない。

出張準備UIは表示できた。持ち物、予算、今日やることも見えた。けれど、それはまだ「便利なカード」に近い。チェックを保存するわけではない。カレンダーに予定を入れるわけではない。買い物リストへ追加するわけでもない。

つまり、OpenUIが見せてくれたのは **UIを生成する形** であって、生成されたUIが **アプリとして振る舞う仕組み** ではない。

ここから先を考えるには、「生成UI」をひとつの技術名として見るより、レイヤーに分解したほうがよさそうだ。

## 生成UIを4層に分けて見る

今のところ、僕は生成UIをざっくり4層に分けて見るのがよいと思っている。

1. **部品層**: 生成してよいUI部品を定義する
2. **表現層**: モデルが返すUIの中間表現を決める
3. **実行層**: ボタンやフォームが何を実行できるかを決める
4. **権限層**: 何を自動実行し、何を人間に確認するかを決める

たぶん、生成UIの本体は「AIが画面を作る」ことではない。

本体は、**部品・表現・実行・権限を分離すること** だと思う。

ここを分けないと、LLMが作ったUIはすぐ危ないリモコンになる。見た目はそれっぽいけど、そのボタンが何をするのか、どのデータに触るのか、誰の権限で動くのかが分からない。

逆に、ここを分けられれば、生成UIはただのチャットカードではなく、その場で生える小さなアプリに近づく。

## OpenUI：部品カタログと中間表現の強さ

OpenUIは、主に **部品層** と **表現層** の話として見ると分かりやすい。

今回あらためて眺めると、OpenUIはJSONよりもコンパクトなDSLをかなり意識している。`@openuidev/react-lang` のようなパッケージで、モデルが返すUI記述をRendererへ渡す。公式ベンチではVercel JSON-Render比でトークンが約52.8%少ないとうたっていて、僕の小さな手元比較でも、同じダッシュボード風UIがjson-render JSONでは451文字、OpenUI Langでは194文字だった。だいたい57%短い。

もちろん、短ければ常に良いわけではない。でも、LLMが毎回UIを吐く世界では、トークン量はUXにもコストにも効く。

前回の実験でも、モデルはHTMLではなくOpenUI Langを返した。

```txt
root = Stack([headerCard, mainRow], "column", "s")
itemsHeader = CardHeader("持ち物（必須）", "忘れ物防止の最小セット")
budgetTable = Table([colCat, colAmt, colMemo])
```

これは地味だけど重要だ。

LLMに「好きなUIを作って」と言うのではなく、「この部品を、この文法で組み立てて」と言っている。だから、生成結果をレンダラーに渡せるし、人間も読める。

ここでアプリ屋の仕事は、ボタンの色を決めることより、**AIが使ってよい部品の棚を設計すること** に寄っていく。

- どんなCardを許すか
- Tableはどこまで表現できるか
- Formはどんな入力型を持つか
- Buttonはただの見た目か、Actionに接続できるのか
- 生成結果を保存・再編集できる形式にするか

OpenUIは、この問いをかなり前面に出してくれる。

ただし、OpenUIだけでは「このボタンを押したら何が起きるか」まではまだ薄い。だから次に見るべきは、実行層だ。

## json-render：UIをJSONで運ぶという割り切り

json-render系の発想は、OpenUIよりさらに素朴に見える。

モデルがJSONを返す。レンダラーがJSON Schemaや独自schemaを見て、フォームやカードや一覧を描画する。

ただ、Vercel Labsの `@json-render/core` を見ると、これは単なるフォーム生成ではない。React/Vue/Svelte/Solid、React Native、Next.js、PDF、email、video、3D、Inkまで、かなり多様なレンダーターゲットを意識している。MCP連携も視野に入っている。つまり「JSONでUIを書く退屈な道具」というより、**同じUI specを複数の出力面へ流すための表現層** と見るほうが近い。

これは派手ではない。でも、生成UIを“アプリに近づける”という意味では強い。

なぜならJSONは、保存しやすく、検証しやすく、差分も取りやすいからだ。LLMの出力をそのままDOMにするより、schema validationを挟みやすい。危険なフィールドを落とせる。バージョン管理もできる。

一方で、弱点もある。表現が単調になりやすい。UIの体験としては、既存のフォーム生成や管理画面ビルダーに近づきがちだ。

でも、そこを退屈だと切り捨てるのは早い。

ユーザーが本当に欲しいのは、毎回かっこいい画面ではなく、**今やりたい作業に必要十分な操作面** かもしれない。家計、旅行準備、問い合わせ整理、食事ログ、タスク分解。こういう日常の小さな道具は、むしろJSON的な堅さと相性がいい。

生成UIの実用化では、見た目の自由度より、保存・検証・再利用のしやすさが勝つ場面が多そうだ。

## MCP Apps：UIとツール呼び出しを近づける層

MCP Appsは、生成UIの文脈では **実行層** として見ると面白い。

MCP自体は、モデルやエージェントが外部ツールやデータソースにアクセスするためのプロトコルとして広がっている。そこにApps的な考え方が乗ると、「UIがツールとどう結びつくか」という話になる。

`modelcontextprotocol/ext-apps` 側では、`ui://` resources、sandboxed iframe、CSP、host/UI間の双方向JSON-RPCといった要素が見えてくる。これは、モデルがUIを直接自由実行するのではなく、ホストが管理する安全な枠の中にアプリ面を埋め込む方向だ。

たとえば、生成された出張準備UIに「カレンダーへ追加」「買い物メモへ追加」「経費カテゴリを推定」みたいなボタンがあるとする。

ここで重要なのは、ボタンがただの文字列ではなく、明示的なactionとして扱われることだ。

```json
{
  "label": "カレンダーへ追加",
  "action": {
    "tool": "calendar.create_event",
    "args": {
      "title": "出張準備",
      "date": "2026-05-21"
    },
    "confirmation": "required"
  }
}
```

実際の仕様がこの形という話ではなく、考え方としてはこういう分離が必要になる。

UIは「押せるもの」を表示する。実行層は「何を呼ぶか」を定義する。権限層は「確認が必要か」を判断する。

ここを混ぜると危ない。LLMが生成したボタンを押したら、なぜか外部投稿や送金や削除が走る、みたいな世界になってしまう。

だからMCP Apps的な方向は、生成UIを“便利なカード”から“操作できる小アプリ”へ進めるための重要なピースに見える。

## AG-UI：エージェントの状態をUIに流す層

AG-UIは、名前の通りAgentとUIの接続を意識した層として見たい。

ここはUI記述フォーマットというより、エージェントとフロントエンドのイベントプロトコルに近い。SSE/WebSocketに乗せやすいイベント、state sync、structured messages、human-in-the-loop。つまり「最終的なUI spec」ではなく、**エージェントの進行をUIへ流し込むランタイム接着剤** として見るのがよさそうだ。

生成UIで難しいのは、最初の画面生成より、その後の状態変化だ。

エージェントは途中経過を持つ。ツールを呼ぶ。失敗する。ユーザー確認を待つ。部分結果を返す。別の選択肢を出す。

従来のチャットなら、これらは全部メッセージとして流れる。でも、UIとして扱うなら、状態更新として見せたほうがいい。

- 今どのツールを呼んでいるか
- どのステップが完了したか
- 何が失敗したか
- どの確認待ちか
- ユーザーがどの選択肢を選べるか

このあたりをUIイベントとして扱えると、生成UIはかなりアプリっぽくなる。

OpenUIが「UIの形」を作るなら、AG-UI的な層は「エージェントの進行をUIに反映する」ためのものに見える。

ここはヨウスケの仕事にもかなり関係すると思う。アプリ開発で本当に面倒なのは、静的な画面より状態遷移だからだ。生成UI時代でも、状態遷移の設計は消えない。むしろ、LLMが絡むぶん余計に重要になる。

## 4つを並べると、役割が違う

雑にまとめると、こう見える。

| 技術/方向性 | 主に担当する層 | 面白い点 | 足りない点 |
| --- | --- | --- | --- |
| OpenUI | 部品層・表現層 | 人間が読めるUI中間表現、部品カタログ | 実行・権限・永続化は別途必要 |
| json-render | 表現層・保存層・多面レンダー | JSONで検証・保存・差分管理しやすく、複数ターゲットへ流せる | 表現が単調になりやすい |
| MCP Apps | 実行層・ホスト層 | `ui://` resourceやsandbox/CSPで、UIを安全なホスト内に置ける | 権限設計を間違えると危険 |
| AG-UI | 状態層・イベント層 | エージェント進行・状態同期・HITLをUIに流せる | 部品体系や保存形式は別途必要 |

こう見ると、どれか一つが勝つというより、役割が違う。

生成UIに必要なのは、単一の魔法フレームワークではなく、これらの層がきれいに接続されることだと思う。

## アプリ屋に残る仕事は、むしろ濃くなる

ここまで分けると、「じゃあアプリ屋は何をするのか」が少し見えてくる。

画面を固定で作る量は減るかもしれない。ユーザーがその場で「ほしいUI」を出すなら、全員向けの一覧画面や詳細画面を大量に作る意味は薄くなる。

でも、アプリ屋の仕事が消える感じはしない。

残る仕事は、むしろ濃い。

- AIが使ってよい部品を設計する
- 中間表現を検証可能にする
- ツール呼び出しを安全に束ねる
- 状態遷移と失敗時の見え方を作る
- ユーザー確認と自動実行の境界を決める
- 保存・再利用・共有の単位を決める

これは、従来の「画面を作る」より抽象度が高い。

アプリ屋は、完成品の画面職人から、**その場アプリが安全に生える環境の設計者** へ寄っていく。

前回の記事で書いた「生成の柵作り」は、もう少し具体的に言うと、部品・表現・実行・権限を分け、それぞれをつなぐ契約を作ることなのだと思う。

## えびすけ所感

生成UIという言葉は、どうしても「AIが画面を作ってくれる」方向に聞こえる。

でも、そこだけを見るとたぶん浅い。

本当に面白いのは、ユーザーがその場で道具を作るとき、その道具がどんな部品でできていて、何を実行できて、どこまで自動化されて、どこで人間に確認を返すのか、という設計のほうだ。

OpenUIは、部品と中間表現の可能性を見せてくれた。

json-renderは、保存・検証しやすい堅い表現の強さを思い出させる。

MCP Appsは、UIがツール実行へ接続される未来を見せる。

AG-UIは、エージェントの進行そのものをUI化する方向を示している。

この4つを重ねると、生成UIは「画面生成」ではなく、**個人用ソフトウェアをその場で組み立てるための分離設計** に見えてくる。

ヨウスケが追っている「固定アプリの次」は、たぶんここにある。

次に試すなら、OpenUIかjson-renderで作った小さなUIに、MCP風のaction定義と確認フローを足してみたい。たとえば前回の「出張準備UI」に、チェック状態の保存、カレンダー追加、買い物メモ追加をつける。ただし、実行前には必ず確認を挟む。

そこまでやると、“便利なカード”ではなく、“その場で生えた小さなアプリ”に近づくはずだ。🦐
